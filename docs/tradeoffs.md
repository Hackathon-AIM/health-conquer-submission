## 2. 더 붙일 후보 — 값이 큰 순서

### A. 되묻기 전에 잠정 안내를 준다 (provisional-first) — **추천**

지금 `app.py`는 이렇게 끝난다.

```python
if route.context == "missing_critical" and route.ask_back:
    return route.ask_back          # ← 질문 한 줄. 그게 전부다.
```

되묻는 판단 자체는 옳다. 문제는 **그 턴의 내용이 0**이라는 것이다.

- 맥락인지(24.7%)는 "되물었나"만 보지 않는다. 되묻기 전에 **안전하게 쓸 수 있는 걸 줬나**도 본다.
- 완전성(4.0%)과 의사소통(21.2%)에서 한 줄짜리 턴은 얻을 게 없다.
- 프론티어 심사에서 임상의가 읽었을 때, 질문만 던지는 답은 인상이 나쁘다.

**비용 0으로 가능하다.** 라우터가 이미 `ask_back`을 만들고 있으므로, 같은 JSON에
`provisional`(2~3문장의 조건부 안내) 필드를 하나 더 요구하면 FM 호출이 늘지 않는다.

- 얻는 것: 되묻는 턴이 빈 턴이 아니게 된다
- 잃는 것: 라우터 출력 토큰 약간 (512 예산 안)
- 위험: 낮음. 지시순응 루브릭의 "되묻기" 요구는 그대로 만족한다

### B. 응급 안전망 프리픽스 — **추천 (안전망 형태로만)**

`router.py`의 `rule_urgency`가 응급을 강제하지만, **119 문장 자체는 모델이 쓴다.**
결정론 문구는 `submission/safety.py`에 있는데 서빙 경로에서 import되지 않는다(죽은 코드).

- HealthBench의 emergency referral은 최악값에 민감하다. 한 번 놓치면 크게 깎인다.
- 실측에서는 모델이 첫 문단에 119를 넣었다(시나리오 ② 통과). 즉 **평소엔 잘 한다.**
- 그래서 항상 붙이면 중복이 되고, 중복은 의사소통 감점이다.

**정답은 "항상"이 아니라 "놓쳤을 때만"이다.** 응급 판정인데 답변 첫 200자에
`119|응급실|즉시`가 없으면 그때만 결정론 문구를 앞에 붙인다.

- 비용: 0s
- 위험: 사실상 0 (평소 경로를 건드리지 않는다)
- 이미 `_EMERGENCY_LEAD` 정규식이 있어 판정 코드가 그대로 재사용된다

### C. 대화 이력 상한 — **추천 (보험)**

`generation.py`는 이력을 그대로 넘긴다.

```python
convo.extend(messages)      # 상한 없음
```

여기에 검색 근거까지 얹힌다. 긴 멀티턴이 오면 `input_limit_exceeded`로
**그 턴이 통째로 0점**이 된다. 우리 `l2.py`는 이 사고를 겪고 축출 로직을 넣었다
(실측: `tool_result 12,000자 × 8건 = 96,000자` → 초과).

- CoEval 대화가 몇 턴인지는 모른다. 그래서 이건 개선이 아니라 **보험**이다.
- 비용: 코드 몇 줄, 지연 0
- 위험: 상한을 너무 낮게 잡으면 맥락을 잃는다 → 넉넉하게(예: 최근 12턴 / 24,000자)

### D. 비평 체크를 **규칙으로만** 4개 — **추천**

`critic.py`의 13개 체크리스트 중 LLM 없이 판정 가능한 것이 있다.

| 항목 | 규칙으로 되나 | 비용 |
|---|---|---|
| `safety_first` (응급 안내가 첫 문단) | 된다 → 위 B와 동일 | 0 |
| `dur_warning_present` (안전 경고가 상단) | 된다 → 이미 우리 게이트가 맨 앞에 넣는다 | 0 |
| `language_matched` (질문과 같은 언어) | 된다 (한글 비율) | 0 |
| `no_hedging_overload` (과잉 유보) | 부분적 ("훈련받은 경우에만" 류 정규식) | 0 |

나머지 9개(`grounded`, `persona_matched` …)는 판단이 필요해서 LLM이 있어야 한다 → 아래 E.

### E. 루브릭 비평 패스 전체 (`critic.py`) — **보류. 가장 아쉬운 항목**

이론상 최대 레버리지다. "좋은 답을 써라"(무한한 선택지)를 "응급 안내가 첫 문단에
있나?"(예/아니오) 13개로 쪼갠다. 확증 편향 때문에 자기비판이 안 되므로 별도 호출이어야 한다.

**그런데 예산이 없다.**

```
현재      중앙값 13.9s · 최대 24.8s
비평 +1회                  +5~10s
재작성 +1회                +5~10s
────────────────────────────────
예상      중앙값 25s  · 최대 45s      → REQUEST_BUDGET_S=40 초과
```

그리고 75초 예산 트라이얼이 **0.00점**을 받은 실측이 있다. 늦은 답과 없는 답이
같게 채점된다면, 품질을 위해 지연을 사는 거래는 성립하지 않는다.

- 조건부 적용(안전 경고가 있을 때만 비평)도 생각할 수 있지만, 하필 그 경로가
  이미 가장 느린 경로다.
- **재개 조건**: 지연 여유를 다시 측정할 시간이 있고, 트라이얼을 한 번 더 태울 수 있을 때.

### F. BGE 리랭커 (`rerank.py`) — **기각**

torch가 딸려와 이미지가 수 GB, 빌드가 수 분. 5분 제한에서 이건 기동 실패 리스크다.
게다가 MCP가 서버측에서 이미 청킹·랭킹을 한다. 우리가 다시 랭킹할 이유가 약하다.

### G. `l2.py` 하네스 통째로 — **기각**

CoEval 3연속 기동 실패(`exit 1`)의 당사자다. **원인을 규명하지 못했다.**
원인 모르는 실패를 다시 들이는 건 기대값이 음수다.

### H. 세션 슬롯 (`session.py`) — **보류 (중복 투자)**

"1턴 음주를 3턴이 100% 기억한다"는 좋은 아이디어지만, 지금 구조에서 이미 커버된다.

- 안전 경고: `drug_safety.guard`가 **대화 전체 텍스트**에서 위험인자를 뽑는다 → 이미 100%
- 답변 본문: 베이스라인이 full history를 generation에 넘긴다 → 실측 ①에서 실제로 기억했다

남는 이득이 얇다.

## 4. 아직 안 풀린 것 — 그리고 반증된 가설 하나

### 4-1. "검색 예산이 모자라 본문을 못 연다"는 **틀렸다**

예산을 5로 올리고 재측정한 결과:

```
retrieval: status=no_evidence items=0 calls=1
  retrieval· index_get_relevant_nodes({"corpus_tag":"guideline",
      "query":"chronic kidney disease blood pressure target guideline recommendation","k":5})
```

**`calls=1`이다.** 예산에 걸린 게 아니라 모델이 **한 번 찾아보고 스스로 포기했다.**
예산을 늘려도 안 쓴다. 가설이 틀렸다.

강화한 추적 로그가 진짜 원인을 보여줬다.

```
index_get_relevant_nodes({"corpus_tag":"hira", …}) → 5,969자 · cite_uid +0
index_get_relevant_nodes({"corpus_tag":"hira", …}) → 5,176자 · cite_uid +0
index_get_page_content({"corpus_tag":"hira","doc_id":"nfill",
                        "start_page":32,"end_page":33})  → 2,990자 · cite_uid +1
index_get_relevant_nodes({"corpus_tag":"hira", …}) → 5,629자 · cite_uid +0
index_keyword_search({"corpus_tag":"hira", …})     → 10,490자 · cite_uid +0
```

**임상 가이드라인 질문인데 5회 전부 `corpus_tag:"hira"`(심평원 급여기준)를 뒤졌다.**
가이드라인 코퍼스는 `"guideline"`이다. 검색이 고장난 게 아니라 **엉뚱한 서랍**을 연 것이다.
(첫 실행에서는 `"guideline"`을 골랐다가 1회 만에 포기했다 — 선택 자체가 불안정하다.)

그 결과 답변은 이렇게 나왔다.

> KDOQI 2022 및 KDIGO 2021 가이드라인을 기준으로 … **수축기 ≦ 120 mmHg** … 권고됩니다 **[1,2]**

근거는 **1건**인데 인용은 **[1,2]** 이고, 그 1건은 HIRA 급여기준 32–33쪽이다.
KDOQI/KDIGO 내용이 거기서 나왔을 리 없다. **가짜 인용에 진짜 근거를 매단 형태**로,
읽는 사람이 "확인된 사실"로 받아들이기 때문에 인용이 아예 없는 것보다 나쁘다.

#### 그래서 고친 것

| 고친 것 | 방법 |
|---|---|
| 코퍼스 오선택 | `도메인 → corpus_tag` 를 코드로 고정 (`guideline_index→guideline`, `hira_updates→hira`). 어느 서랍인지는 도메인이 이미 안다 — 모델 재량에 맡길 이유가 없다 |
| 근거 수를 넘는 인용번호 | 유효 범위 밖 번호만 제거. `[1,2]`·`[1, 2]` 형태도 처리하고, 번호가 전부 유효하면 손대지 않는다 |
| 역할 라벨 누수 | 답변이 `Assistant` 한 줄로 시작해 나왔다. 채팅 템플릿 누수 — 첫 줄만 제거 |

### 4-2. 인용 0건 — 우선순위는 낮다

근거를 받은 턴에서도 `[1]`이 없다. 모델이 `Cite these as [1], [2]`를 무시한다.

다만 **인용 마커 자체는 점수와 직결되지 않는다.** 채점 축에 "인용"은 없다.
값이 있는 건 근거를 **읽고 쓴 답**이고, 실측 ⑥에서 제41조 세부 내용이 답변에 들어간 걸 보면
근거는 실제로 쓰이고 있다. 4-1이 먼저다.

### 4-3. 되묻기 턴이 되묻지 않는다 (실측)

③을 다시 돌렸더니 `context=missing_critical` 경로로 빠졌고, 나온 것이 이거다.

> 와파린 복용 중 아스피린 병용은 출혈 위험 증가로 매우 위험할 수 있습니다. 신장기능, 간기능,
> 빈혈 여부, 와파린 용량, 적응증 및 아스피린의 목적을 확인해야 합니다. 단독 판단하지 마세요.

프롬프트는 "한 문장의 질문"을 요구했는데 **질문이 아니다.** 확인할 항목을 나열하고 끝난다.
답도 아니고 질문도 아닌 턴이다. §2-A가 필요한 이유가 여기 있다.

(그래도 2.4초에 우리 병용금기 경고가 맨 앞에 붙었다 — 안전 측면에서는 이 턴이 제 몫을 했다.)

## 5. 결론

지금 붙일 값이 있는 건 **A·B·C·D 네 개뿐이고, 넷 다 FM 호출을 늘리지 않는다.**
지연을 사는 개선(E)은 이 대회의 채점 규칙과 정면으로 충돌한다.

가장 큰 레버리지는 새 기능이 아니라 **§4의 재측정**이다 — 검색이 본문을 여는지 아닌지가
정확성 43%를 좌우한다.
